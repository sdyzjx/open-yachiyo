# Android 麦克风回录与扬声器试听验收

> 类型: experiment
> 状态: done
> 负责人: codex（agent/realtime-tts）
> 更新: 2026-10-13
> 关联: ../testing/TC-android-companion-integration.md, ../testing/TC-device-hub.md, ../../apps/android/app/src/main/java/com/yachiyo/companion/audio/MicController.kt, ../../apps/gateway/deviceHub/audioInput.js

## 背景与假设

真机原生麦克风上传生成了 16 kHz 单声道 WAV，但 ASR 返回 `Empty ASR transcript`。当时自动化脚本同时在手机播放一段已知参考语音，并记录到 `maxRms=0.208`。需要区分三种可能：PCM/WAV 编码或传输损坏、录音窗口截断、以及麦克风实际上没有收到可识别语音。

本实验只分析已经生成的本地音频和日志，不调用模型 API、不读取凭据、不占用真机。随后将用户亲自完成的扬声器试听作为独立观察记录，避免用播放回执代替实际可听性。

## 实验环境

- 日期：2026-10-13
- 设备：小米 6，Android 15 ROM
- 隔离验收目录：`/tmp/yachiyo-companion-acceptance`
- 麦克风录音：`data/device-audio/mic-d23c8c95-1791823517037-0.wav`
- 参考语音：`voice/qwen-tts-real.wav`
- 参考文本：`这是八千代手机语音测试。`
- 相关日志：`acoustic-after-savings.log`、`gateway.log`
- 工具：`file`、`ffprobe`、`ffmpeg`、只读 Node 分析脚本

上述临时音频、频谱图和分析中间文件没有加入 Git。

## 方法

1. 检查 RIFF/WAVE 头、文件长度、采样率、声道、位深、数据段长度和时长。
2. 按 Android 上传契约的 100 ms 块检查块数、尾块、块边界差分、零样本和重复块；同时尝试大端序和错一字节解释，排除字节序或对齐错误。
3. 对麦克风录音和参考音频计算整体电平、50 ms 包络、频带能量、频谱中心以及波形相关性；生成声谱图检查基频与谐波结构。
4. 用 stream id 与 playback request id 的时间戳估算播放窗口，并核对 `voice.playback.started/ended`。
5. 对比此前同设备录音的启动段，判断高 RMS 是否代表讲话。
6. 记录音量控制的实际读回值；将后续用户在真实可听音量下的试听与此前麦克风回录分开判定。

## 数据与观察

### PCM、WAV 与传输完整性

| 项目 | 麦克风录音 | 参考音频 |
|---|---:|---:|
| 容器 / 编码 | RIFF WAV / PCM s16le | RIFF WAV / PCM s16le |
| 采样率 / 声道 | 16 kHz / mono | 24 kHz / mono |
| 时长 | 4.650 s | 2.560 s |
| 样本数 | 74,400 | 61,440 |
| 文件大小 | 148,844 bytes | 122,924 bytes |
| RMS / peak | -28.66 / -12.43 dBFS | -24.02 / -7.07 dBFS |

麦克风文件大小精确等于 44-byte WAV 头加 148,800-byte PCM 数据。PCM 由 46 个完整 100 ms 块和一个 50 ms 尾块组成，数据长度为偶数。块边界最大跳变为 0.0127，而全体相邻样本差分 p99 为 0.0116，没有边界断裂证据。大端序或错一字节解释都会得到 RMS 约 0.575、频谱平坦度约 0.503 的近满幅噪声，因此小端序与字节对齐正确。

### 录音内容

| 区间 | RMS | 频谱中心 | `<100 Hz` 能量 | `300–3400 Hz` 能量 | 观察 |
|---|---:|---:|---:|---:|---|
| 麦克风 0–0.30 s | 0.0060 | 842 Hz | 3.4% | 53.3% | 低电平启动噪声 |
| 麦克风 0.30–0.80 s | 0.1072 | 44.9 Hz | 98.4% | 0.3% | 强低频漂移/瞬态，造成高 RMS |
| 麦克风 0.80–3.35 s | 0.0129 | 279 Hz | 60.9% | 10.3% | 约 97–100 Hz 与 64–70 Hz 低频成分，无语音谐波 |
| 麦克风 3.35–4.65 s | 0.0105 | 239 Hz | 39.8% | 17.9% | 低电平背景与瞬态 |
| 参考音频 0–2.56 s | 0.0630 | 1,889 Hz | 0.0% | 77.7% | 清晰基频、共振峰与多阶谐波 |

参考音频与麦克风录音的全波形最佳相关系数为 0.039；200–450 Hz 带通后仍只有 0.077。50 ms RMS 包络最佳相关系数为 0.359。声谱图中参考音频的连续语音谐波没有出现在麦克风录音中。

此前一段 3.45 秒同设备录音也在 0.3–0.9 秒出现近似低频包络；它与本次录音启动段的下采样相关系数为 0.97。该信号可重复，但不是可识别语音频谱。`maxRms=0.208` 只能说明出现过大幅低频信号，不能证明麦克风录到了讲话。

### 播放窗口与实际音量更正

麦克风 stream id 时间戳比本地播放 request id 早 571 ms；4.65 秒录音窗口足以覆盖 2.56 秒参考音频。`gateway.log` 同时记录了该 request 的 `voice.playback.started` 与 `voice.playback.ended`，因此不是 WebAudio 源节点提前终止或录音窗口截断。

但先前通过 `cmd media_session ... --set` 尝试把媒体音量从 0/25 设置到 5/25 时，命令静默返回却没有生效，真实读回始终为 0。验收记录中“已在 5/25 音量进行同机声学回录”的描述不成立；该 WAV 实际是在媒体音量 0 下录制，不能用于判断同机回声抑制或扬声器到麦克风的声学路径。

随后用户使用实体音量键把媒体音量调到 17/25（68%），应用音量为 1，播放同一 `qwen-tts-real.wav`，并观察到 `voice.playback.ended`。用户明确反馈“能听清，音量正常”。这证明真机 WebAudio 到物理扬声器的输出链路已经通过实际听感验收。此次试听没有同步录制麦克风，因此不能据此判定 ASR 闭环通过。

## 结论与决策

Android PCM 分块、Base64 传输和网关 WAV 封装没有发现编码或截断错误。ASR 返回空的直接原因是送入服务的 WAV 没有可识别的讲话频谱。

此前声学回录时媒体音量实际为 0，因此现有数据不足以把空录音归因于同机回声抑制、麦克风 DSP 或物理声学耦合。不得基于该文件修改网关封装或 Android PCM 代码。

物理扬声器播放已由用户在 17/25 系统音量、应用音量 1 下确认通过；`voice.playback.ended` 与实际听感一致。TC-COMP-008 和 TC-HUB-016 的播放部分通过，麦克风采集状态和文件生成通过，真实讲话 ASR→pi 回复仍未通过。

## 后续动作

- 下一次麦克风验收使用用户直接讲话，或使用第二台设备/外部扬声器播放参考音频，避免再次把静音的同机回放当作语音输入。
- 开始录音前读取并记录实际媒体音量；若通过命令修改，必须再次读回确认。系统命令静默返回不能视为成功。
- 只执行一次已授权的真实 ASR 验收，不循环调用付费接口；记录 transcript、设备会话回复与音频质量。
- 若在确定可听的外部语音输入下仍无语音频谱，再分别比较 `MIC`、`VOICE_RECOGNITION` 和设备支持时的 `UNPROCESSED` 音源。
